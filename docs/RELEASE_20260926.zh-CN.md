# 2026-09-26 发布候选记录

本轮把 `codex/project-hardening` 中已有的加固实现整理为可审阅的发布候选，延续 1 篇 Blog、5 篇 Saying、空 Trace 的内容基线。没有新增个人资料或恢复历史内容。

## 实施与修正

- 功能分支已同步远端生产基线 `ef3f99b`；该合并与原开发基线的文件内容一致。
- 依赖、Pure/Waline 补丁、内容数据层、客户端生命周期、响应式媒体和 CI 工作流随各自提交进入版本管理。
- 本机验证使用独立的 Node 24.18.0 / Bun 1.4.0，与 `.node-version`、`packageManager` 和 CI 一致；不改变系统安装版本。
- 修正生命周期回归中系统配色检查的等待条件：CDP 返回不意味着浏览器已经派发媒体查询事件；原来的固定 80ms 等待会偶发失败。改为等待渲染帧，并在两秒期限内检查实际主题，保留失败门槛和手选主题检查。
- 开发文档改为实际使用的 Node Astro CLI 入口；README 和交接文档不再把首轮“尚未提交”当作永久状态。
- 工作区已有的 `.agents/` 与 `skills-lock.json` 属于独立的本地技能安装，不纳入博客发布提交。
- GitHub CLI 的 Fork 默认目标原为上游，现已在本地指向 `Susurrium/susurrium.github.io`；发布命令显式指定 `--repo`。
- 首次 Linux CI 揭示 Pure 的 Steps/Tabs 插件直接导入但未声明的 `rehype`。项目补充锁定 `rehype@13.0.2`，并纳入环境预检；它仅用于构建期 HTML 处理，不增加浏览器请求。最终候选使用仓库外的独立 worktree 验证，避免嵌套检出向上解析到旧 `node_modules`。

## 发布与后续维护

发布顺序为功能 PR → develop → 发布 PR → main → 手动 Pages 工作流。具体部署提交、时间和结果以 GitHub Actions 记录为准；本地检查不能替代远程检查。

本轮完成后，日常工作以内容维护为主：

1. 用 `bun run new --type blog --folder --language zh-CN "标题"` 或 `bun run new --type trace "标题"` 创建默认草稿；完成正文后再设为公开。
2. Trace 需要长期固定封面时同时填写 `cover` 与 `coverAlt`；新增媒体后检查资源预算。
3. 剩余体积建议涉及原始图片、文章截图及部分装饰资源。文章截图已有 Astro 优化产物；进一步压缩需逐项比较画质和裁剪，不扩大预算豁免。
4. 定期人工复查第三方音乐、地图、评论、友链和依赖审计；目前不增加定时工作流或自动发布。

本地日志和截图保存在被 Git 忽略的 `artifacts/release-20260926/`。生产发布失败时保留当前线上版本，修复候选并重新执行门禁，不绕过失败检查。
